# Project data

deck.json has schema:1, title, version (default 1), slides and optional order/motion. Each slide has a unique safe id, label, section, topic, sourceNumber, header (full/number/none), blocks and optionally html. Optional `navigationLabel` and `navigationTopic` override navigation strings; raw labels/topics remain in source metadata. Default navigation removes only a one or two digit slash prefix, or a punctuation prefix matching sourceNumber; explicit navigation strings preserve intentional numbered sections. Optional `background` is `{type:"color",value:"#RRGGBB"}`, `{type:"gradient",value:"linear-gradient(...)"}`, or `{type:"image",asset:"assets/file.png",focal:"50% 50%",size:"cover"}` (`position` aliases `focal`). Backgrounds fill the 1920×1080 slide independently of the 1696×874 safe content area; local images are embedded for offline use. IDs start with a letter and contain letters/digits/underscore/hyphen. Order contains included slide IDs only; slides can retain excluded records. Section/topic stay with the ID, never with its current array index.

extract_pptx.py produces blocks: text (paragraphs and inline runs), table (rows/cells/paragraphs), chart (series/categories/values), image (asset), group (ancestry), geometry and unsupported. Source part/object ID and transforms retain traceability. Direct `p:bg` XML is retained as `sourceBackground` evidence; picture objects exactly matching the slide canvas are flagged `backgroundCandidate` and keep raw EMU geometry. These are review evidence, not automatic rendering decisions: map a confirmed local asset to the slide `background` field or declare a rendered fallback. It extracts content rather than implementing PowerPoint inheritance/layout/rendering. Shape geometry and SmartArt need visual reconstruction or a declared rendered fallback. Do not claim arbitrary PPTX 1:1 import. Current extraction audit covers visible slide XML text; compare chart values separately and inspect master/layout material in the source proof.

For reviewed output, slide.html replaces the assembly draft for that slide. Use semantic h1/h2/p/lists/tables and SVG where appropriate. It is inserted inside .gd-content, within the independent .slide-inner motion layer; keep UI outside it. Refer to local assets as src="assets/name.png"; the builder embeds them. The builder rejects scripts, event handlers and javascript URLs in body markup. It is not an arbitrary HTML application importer. Local assets/fonts must reside inside the project directory. Remote resources are not an offline asset solution.

Source notes are stored in the project and deliberately omitted from public HTML. Only include notes in a public/presenter feature when requested. PPTX footer/date/page placeholders are separated from body. Automatic fields and ambiguous geometric footers require review; do not delete meaningful source content by position alone.

The shell's SalesKitUI.setOrder([...]) validates IDs and prevents empty/duplicate orders. SalesKitUI.exportDocument('work') returns a next-version standalone HTML with all slides and the selected order; 'bundle' retains only selected slides. GigaDevDeck.getState() exposes the active selection/settings. prepareExport() is a one-way preparation for an isolated export page, not a user editor toggle. It commits text, closes dialogs, finishes motion and reveals per-slide metadata. Excluded slides stay excluded; numbers reflect current order.

The runtime text editor supports ordinary HTML content. Authored journal targets use a unique `data-source-id` on one text element per slide; the editor assigns its own stable `data-eid`. Preparation `sourceId` must resolve once, and its before/after value must agree with the target and applied state. Text inside SVG, raster artwork, media, canvas or external iframes is not promised editable. For meaningful labels, prefer HTML text or explicitly declare a graphical fallback.

Wheel/touch navigation in the accepted shell v06 matches SalesKit v25: native continuous scrolling, no wheel interception, no mandatory snapping. The paused WAAPI opacity/blur follows scroll position and immediately follows reversal. A stopped wheel may leave the deck between slides; metadata identifies the nearest slide. Keyboard/clicker navigation retains its separate timed exit/entry. Do not equate these two input paths or add a per-gesture lock. The checker exercises small wheel deltas, reversal and multi-slide scrolling, not just completed slide changes. Header counter alignment remains independent of breadcrumb visibility.

The browser uses `--gd-scroll-height` for a full-window scroll page, and places the fixed 1920×1080 composition inside it with the same fit/safe-area margins. The scrollport must reach the top and bottom of the window, including in tall windows and presentation mode. A scaled 1080px scroll viewport would introduce letterbox clipping through text during scroll. Export/print reset scroll height to 1080 and composition offset to 0. Check the actual ancestor clip rectangles and partial-scroll screenshots; animation curve parity is insufficient.

The scrollport and page heights are unscaled viewport pixels. `--gd-view-scale` affects only the intrinsic content. The shared v25 easing/timing is retained; scroll uses an independent motion layer at the v25 responsive zoom, and `--gd-motion-gain` converts keyboard-group blur/translate units using that zoom divided by content fit scale. This prevents double-scaling: same wheel deltas give the same screen displacement, fade progress and effective blur as v25. Test repeated wheel input and reversal at the same viewport; comparing curves at normalized percentages can hide wrong speed.

When a source HTML is available for motion parity, run `node scripts/check_motion_reference.mjs /absolute/reference.html /absolute/candidate.html /absolute/NEW_QA_DIRECTORY`. It replays the same wheel sequence at four viewports and compares actual screen displacement, opacity, blur and clipping. It needs two slides and the SalesKitMotion bridge; it is optional for unrelated source runtimes.

The .slide-inner motion layer fills the 1920×1080 slide and remains separate from fitted .gd-content. Scroll filtering uses the same responsive CSS zoom as v25, so the browser paints blur at the reference resolution; intrinsic 1920×1080 content fits inside it. Keyboard groups still come from the content children, with compensated units for their separate scale. Show and export headers use the same 48px left/right, 30px top, SB Sans Display Regular 20px coordinates at canonical size. Export keeps the moving frame full-size and positions the untransformed 1696×874 safe content at 112,120.

The show header uses the supplied AI_PDLC_Status_v05 reference: SB Sans Display Regular (400), 20px font / 24px line height in intrinsic 1920×1080 units, scaled with `--gd-view-scale`. The show footer counter uses Display Regular 13px/1.2 in screen units. Keep the existing narrow-screen 10px top-navigation floor, other UI/body typography, header positions, palette, metadata logic and export styles. The included Display Regular OTF matches the reference font bytes; avoid synthetic bold or a substituted Text face.

Reading backgrounds fill the entire viewport behind the transparent navigation; the 16:9 composition keeps logical UI gutters. Background paint is a direct child of `.slide-inner`, before `.gd-content`; attach washes to `.gd-slide-background::before` rather than static `.slide::before`. Export/print explicitly reset the paint to 1920×1080. Test both image and gradient backgrounds at partial scroll positions.

Native graphic frames (tables/charts) carry their own `p:xfrm`; shapes/pictures use `p:spPr/a:xfrm`, groups use `p:grpSpPr/a:xfrm`. Consume the recorded own-object transform, not the first descendant transform. Group coordinate transforms and unsupported effects still need review. A missing table transform is a blocker for geometry preservation, not permission to place every cell at zero.

## Legacy structured compositions (Maker 0.20.0+)

For new design work select the [accepted reference pack](reference-pack.md) and author adaptive slide HTML. The schema below remains compatible with existing pinned renderer projects.

A reviewed slide may use `composition` instead of `html`:

```json
{"id":"decision","label":"Comparison","blocks":[],"composition":{"id":"comparison","version":"1.0.0","data":{"title":"Which option fits?","columns":["Criterion","A","B"],"rows":[["Setup","Fast","Custom"],["Support","Standard","Specialist"],["Scale","Small","Large"]],"highlightColumn":2}}}
```

The builder rejects simultaneous html/composition and mismatched pattern versions. It includes scoped composition CSS only when used. Read the selected catalog record/example for fields and capacity. Optional `highlightColumn` is zero-based; omit it for an unbiased factual matrix. Text values accept `{text,sourceId,runs,href}` and card icons accept `{icon,iconAlt,iconSourceId,accent}` on their item. Body paragraph arrays and footer arrays preserve separate source targets. Table sourceId uses `tableSourceId`. Keep source blocks for audit; only composition is rendered. `sampleOnly:true` is reserved for the library-demo deck purpose and cannot appear in an ordinary delivery. See [compositions](compositions.md).
