# Style references

Separate shell UI from slide styling. assets/ui.css and the controller are reusable product behavior; theme JSON and slide.html define the deck's visual system. Do not copy the full source SalesKit CSS/media into every new deck.

First identify each input's role. A source PPTX can supply exact content and a loose direction without making every source composition mandatory. Preserve-design mode follows the source geometry; improve-layout mode preserves its facts/brand direction while correcting hierarchy, density, backgrounds and composition; change-style mode follows the new chosen reference. Infer the mode from the request and resolve only material ambiguity.

A filled PPTX is also a style reference unless the user says to change its style. Start from source fills, ink, accents, divider colors, type roles and graphics; distinguish source evidence from theme defaults and the Maker shell palette. Native theme accent1 alone is not a reliable brand accent: inspect actual slide usage, including direct colors and supplied renders. The [source-style workflow](source-style.md) records this evidence and checks the resulting decisions. “Improve layout” changes hierarchy/composition, not permission to replace the source's visual identity with mint/black or drop its icons.

When no useful style reference is supplied, use the included [accepted composition references](reference-pack.md) and [neutral base kit](base-style.md): anonymous reusable compositions rather than copied source content or logos. The kit is a vocabulary, not an automatic designer. Author appropriate cover/data/process/dense layouts and review them; do not deliver the raw block assembly as the finished design.

Best input: a filled PPTX design reference with a cover, section divider, dense text, table, data chart and image slide. A POTX can provide theme/master/layout evidence, but may not show real compositions. HTML references reveal CSS and components; images give approximate visual direction. Request exact font files only if needed for fidelity and portability.

Compile a small theme JSON: name, themes (['dark'] / ['light'] / ['dark','light']), primary, font CSS stack, colors by available theme (bg/ink/muted/accent/line in #RRGGBB), optional fonts [{family,weight,path}] and css. The file can sit anywhere; asset/font paths resolve relative to the deck project. A one-theme style must not expose an unusable theme switch. Screen calibration operates the five semantic palette tokens; custom hard-coded SVG/CSS colors do not automatically inherit it.

A full style also needs layout choices in slide.html: grids, text scale, white space, framing, image treatment and graphical language. Changing color tokens alone is not a new style. Store those choices in a short project-specific style guide, not in shell JS. Dense material needs a reading-first composition; do not default every slide to a three-card grid.

Show representative cover/data/dense slides alongside the source before propagating an improved or new style. Explain the concrete gain: hierarchy, reading sequence, useful space, table legibility or image treatment. A color/font replacement alone is not redesign. Preserve facts/wording and do not invent chart data. Keep the existing transition baseline; additional choreography is separate. Validate static states before motion.

Resolve primary light/dark theme from the request and source backgrounds/ink; do not classify from one cover image alone. If uncertain, offer one short choice with a recommended theme and optional second theme. Absent a decision, proceed with one stated main theme where safe. A second theme needs deliberate palettes, imagery/contrast adjustments and its own review. The base kit contains both token sets as reusable material; it does not require delivering two themes. Export only the active or explicitly chosen primary theme, with no duplicate decks unless requested.

Treat backgrounds as full-canvas paint through slide.background; illustration/logo fitting belongs to content. Never put a slide-wide image/gradient inside the text-safe frame. Preserve focal position and source cropping where appropriate; explicitly review altered crops. Navigation geometry is independent of text margins and shared between show/static output. Keep source numbering, current page numbers and optional chapter labels separate; source navigation prefixes are not body content.

Default typography is embedded SB Sans Text Regular/Semibold for UI/body and SB Sans Display Regular/Semibold for headings. theme.font changes body; theme.displayFont changes headings (falling back to an explicitly supplied body font for other styles). Set builtinFonts:false to omit the bundled SB pack; supply authorized project font files as needed. Custom fonts with the same family/weight replace their bundled declaration. Original binary metadata is preserved; default source hashes/glyph counts/fsType are in assets/fonts/manifest.json.

Default dark colors match the source v25 computed fills: one continuous bg/shell #050709 across the whole presentation. A supplied style can override both; omitted shell falls back to that style bg. The navigation rail is transparent, with no separate sidebar panel. Its selection fits the active row, including padding, after fonts load and on navigation/reorder/resize. Keep clear hover/current/focus states.

## UI accent and selection roles

The shell uses mint --sk-accent (#9deda5) as a fill in both themes. --sk-on-accent is dark ink (#173923). In the light theme, --sk-accent-text (#2d6b44) supplies readable green accent text and thin indicators; never put the pale mint fill color into small text on white. Neutral --sk-selected-fill/--sk-selected-ink identify selected mode controls by fill contrast. --sk-focus-ring is reserved for keyboard focus; do not add persistent selection strokes. Checkbox and radio states share size, stroke and palette; Composition cards remain neutral; the marked radio identifies their state. Keep non-accent surfaces and hovers grayscale. Empty checkbox/radio boundaries and keyboard focus indicators are functional exceptions to the no-decorative-stroke rule.

Window placement uses an icon toolbar, with four-corner maximize glyphs. Card layout uses named List/Tile segments. Keep their roles visually distinct. For changes to UI colors or states, run scripts/check_ui_contrast.mjs against a generated Maker HTML and a new QA directory. It measures enabled button text/icons and selected-state boundaries in normal/hover/keyboard-focus states for the journal/organizer shell; it does not certify an entire document's accessibility. Inspect real screenshots as well.

Stateful mode switches change ink and fill together without color interpolation; transient interpolation can erase selected-state contrast. Keep slide motion independent.

The neutral default light slide style also uses achromatic background, primary/secondary ink and dividers; green belongs to the accent token. Preserve explicitly supplied brand styles rather than recoloring reference decks automatically.

## Graphics and contrast acceptance

Inventory source graphic instances before authoring. Reuse an icon/illustration when it still serves its role; rework scale, placement, crop or grouping as needed. A replacement must state the preserved role and target. An omission needs a slide-specific reason such as duplicate navigation or irrelevant legacy logo; “decorative” alone does not explain wholesale removal. Text/card layouts are not equivalent replacements for every illustration. Keep local vector assets where supported, and document any raster fallback.

Check image covers with all their copy visible: a full-bleed image can still fail if captions sit on bright areas. Use the fewest necessary interventions (placement, width, localized wash) and inspect the actual 16:9/show and free-reading renders. Do not put a static wash on `.slide::before`; it belongs to the animated background layer. Dense slides need distinct reading groups and appropriate scale; avoid applying the same three-column pattern to every content type. Meaningful air is valid; arbitrary fillers are not.

For deck identity, separate a human-readable title from source filename/version. Preserve original labels in project data. Treat optional list indices as a design decision separate from native page numbering; never remove factual numbers with a broad regular expression.

Before exporting a redesigned deck, render all static HTML pages and fix clipping or text collisions first. Use semantic h1/h2 headings, measure their actual font-loaded line height before positioning the following block, and let tables use a validated frame/grid instead of unconstrained cell offsets. Source geometry is evidence, not a guarantee that changing fonts preserves line wrapping. Check that custom selectors (for example `[data-sk-id]`) match the real shell DOM and that declared washes appear in computed styles and pixels. A successful package build does not excuse overlapping text or a dead contrast rule.
